# 已知限制（Known Limitations）

[English](./KNOWN_LIMITATIONS.md)

记录扩展无法用代码修复的平台/上游约束。每一条都说明限制是什么、为什么存在、代码对此做了什么。
当某条限制解除时（例如某个 Chrome 里程碑默认启用了一个功能），请更新本文件。

## 默认 Chrome ≤156 上 chrome-extension:// 页面中的 WebMCP 被阻止

**状态**：上游平台限制——本仓库无法修复（在未带 dev flags 的正式版/默认 Chrome 上对用户可见）。

**现象**：在**默认（未加 flag）Chrome ≤156** 上，WebMCP（`document.modelContext`
命令式 API——扩展 "WebMCP" 主动控制路线的基础，Wayfinder 043/044）在 `chrome-extension://`
页面中存在但**不可用**：调用 `registerTool` / `getTools` 会抛出

```
SecurityError: document.modelContext cannot be used when document.domain is enabled.
```

Chrome 把扩展源当作启用了 `document.domain` 的源，而 WebMCP 实现拒绝之。普通网页
（`https://…`、`http://localhost`——测试中用 `example.com` 验证过）可以正常注册。

**注意——该阻止与 flag 有关，不是绝对的**（E2E 复核发现）：使用 WebMCP **测试 flags**
（`--enable-features=WebMCPTesting,WebMCP,DevToolsWebMCPSupport`，仓库的 `.mcp.json`
正是这样传给 chrome-devtools-mcp 启动的 Chrome 的）时，扩展源上的阻止被**解除**：
`getTools()` 和 `registerTool()` 在 `chrome-extension://` 页面上可以工作。所以限制恰好是：
*默认/正式版 Chrome ≤156 且没有这些 flags*。这正是扩展要做诚实检测的场景——普通用户的浏览器
不可能有这些 flags，所以对他们 WebMCP 路线会正确地置灰；带 flags 的 dev/test 浏览器则会
正确地亮起。

扩展源支持在上游被标记为 "ongoing development"；Chrome 157 是 WebMCP 默认启用的里程碑，
它是否解除对扩展页面的这个阻止从这里无法验证。

**在实践中意味着什么**：

- 在**默认 Chrome ≤156** 上：只有在 API 实际可用后，Options 页面才能切换到 WebMCP 路线——
  见下面的诚实检测。实际上该区段会保持置灰（**"Requires Chrome with WebMCP enabled"**，
  即"需要启用 WebMCP 的 Chrome"），直到 Chrome 157（或带 flags 的 dev 浏览器）。
- 在**带 flags 的 dev 浏览器**上：完整的 WebMCP 流程（切换路线 → Register → AI 调用
  `excali_canvas` 工具 → Unregister）可以在扩展页面本身上测试。
- 两种情况下 ws + daemon 路线都不受影响。

**代码做了什么**（E2E 发现 → 加固的特性检测）：

- 存在不等于可用：`'modelContext' in document` 在扩展页面上为 `true`，尽管该 API 在那里会抛错。
  `packages/shared/src/agent-bridge.ts` 中的 `isWebmcpUsable()` 会探测一次 API——抛错的调用
  （上面的 SecurityError）会把该特性报告为**不可用**。
- Options 页面使用该探测：在被阻止的源上 WebMCP 区段置灰（"Requires Chrome with WebMCP
  enabled"），而不是亮起后点击失败。
- 页面的 `registerWebmcp` 也会先探测并在不尝试的情况下返回 `false`，所以按钮的失败路径是诚实的
  toast（"无法暴露此画布。请重试，或切换到 ws + daemon。"），而不是裸的 SecurityError。

**何时重新验证**：Chrome 157+ 成为默认渠道时——检查扩展页面能否在无 flags 的情况下调用
`document.modelContext.registerTool`；如果能，去掉探测在抛错时的 catch-all `return false`
（或保留它——web 源上真实的 SecurityError 仍然是需要暴露的回归）。

## 实时协作（1.8.0）

协作功能的设计与平台限制（[COLLAB.zh-CN.md](COLLAB.zh-CN.md)、
[ADR 0003](adr/0003-byo-relay-realtime-collab.md)）。每一条都说明限制是什么、
为什么存在、代码对此做了什么。

### 单文件 20MB 上限，不支持断点续传

**现象**：协作房间中同步的文件（图片、附件）**每文件上限 20MB**，上传不可断点续传——
中断的上传需要重来。

**原因**：中继把每条消息分块到 DO 256KB 上限以下（20MB / 200KB = 每文件 100 块），
且 v1 有意不携带断点续传机制。

**代码做了什么**：file-put 路径在客户端拒绝超限文件并给出明确错误；上限以下的
一切照常工作。

### 每个扩展一个中继

**现象**：扩展同一时刻只连接一个中继——永久如此。接受服务器邀请即替换已存配置，
不存在多中继列表。

**原因**：多中继支持在 ADR 0003 中被永久否决（设计排除项，不是延后）——它消除了
房间邀请所依赖的路由歧义。

**代码做了什么**：服务器邀请解析器和选项页协作区强制执行单配置不变式；房间邀请
从不携带服务器地址。

### 无逐成员吊销

**现象**：成员密钥泄露后无法单独吊销；驱逐走组织级路径——轮换组织密钥、重新签发
服务器邀请、让受影响成员重装。

**原因**：按 ADR 0003 身份自声明（无 PKI）；迷你 CA 被明确否决。

**代码做了什么**：旧成员密钥签署的已存内容仍可通过自包含的 `signer` 字段验证，
轮换不会破坏历史。

### 中继无速率限制（v1）

**现象**：中继参考实现不对流量做速率限制或节流。

**原因**：v1 面向组织私有的小团队部署，运营者信任成员；带宽滥用不在 v1 威胁模型内。

**代码做了什么**：记录在案的行为——中继不适用于公开/多租户运营。

### 非 Cloudflare 自托管中继：仅单节点，无 SLA

**现象**：中继可以自托管在 Cloudflare 之外——自行运行 `workerd`（`pnpm relay:dev`
通过 `wrangler dev` 驱动它；见 [ADR 0010](./adr/0010-self-host-cf-workerd.md)）。
随之而来两条限制：

1. **单节点。** Durable Object 的持久化依赖 workerd 内建的 SQLite cells，落在一台
   机器上。没有复制方案，不存在第二个节点。多节点目前刻意不在范围内（留给后续
   ADR，不是这一个）。
2. **无 SLA。** 本仓库交付的是运行时集成，不是交钥即用的平台。Cloudflare 不为开源
   `workerd` 构建提供 SLA，我们也不代部署者承诺任何 SLA——可用性、备份、TLS 终结
   （在前面挂 Caddy/nginx）与升级都由部署者负责。

**原因**：运行时选型卡在 Ed25519 原始公钥导入上，这是中继 org 签名准入的前提。
[celld](https://github.com/denoland/celld) 曾是首选目标，但 2026-08 试点显示其内嵌
V8 拒绝 `crypto.subtle.importKey("raw", …, {name:"Ed25519"})`，导致每个 org 签名
hello 都被拒。`workerd` 在 2026-09-08 通过了同一探测。

**代码做了什么**：`pnpm relay:smoke` 针对当前运行时断言 Ed25519 原始导入 + 验签
往返（正常与篡改两种输入），因此如果一个运行时在这点上退化，会立即高声失败，
而不是静默把所有成员锁在门外。多节点复制未实现。

### v1 实际为单 org：房间不绑定组织

**现象**：多 org 是计划中的设计，但 v1 实际只有单 org——开发循环只注册一个组织
（`local`），每个客户端只持有一份服务器配置（一个 org 标签），且房间从不绑定组织。
任何被准入到中继的成员，只要拿到某房间的 shareId 就能连进去；org 只决定客户端能
*解密*什么（团队房间：本 org 的 `ck`），而不是能*到达*哪些房间。

**原因**：org 标签和 `ORG_PUBKEYS` 环境变量结构是刻意的向前兼容——数组现在
就接受多个条目，将来多 org 部署无需破坏性变更；按组织隔离房间需要 v1 刻意没有的
org→room 绑定。

**代码做了什么**：`ORG_PUBKEYS` 接受 org 数组；准入用 hello 的 org 签名对该组织
注册的每个密钥逐一验签；没有任何代码比较 hello 的 org 与房间的归属。组织间房间级
隔离是将来的工作，不是 v1 的属性。

### 空房间即消亡

**现象**：房间为空且 Durable Object 被驱逐（约 70–140 秒无活动）时，房间的快照和
文件被删除。任何用户可见的东西都不会在服务器端持久化。

**原因**：按设计——房间是临时叠加层，本地图库才是持久记录（ADR 0003）。

**代码做了什么**：房间列表在本地保存邀请载荷；重进已死房间时提示第一个成员从图库
重新播种。

### 演示模式 × 协作（ADR 0008 — 将于 1.9 发布）

**现象**：2026-08 延后项部分解除——**演示跟随将在 1.9 中发布**。

**已发货内容**：自声明多演示者模型（任意成员均可开始演示），向跟随者单向广播原始视口流，点击名单条目逐人进入跟随，本地平移/缩放手势发生时中断跟随并弹出 toast（"已停止跟随 {name}"）。一次性光标跳转：点击正在演示的成员头像跳转至其当前视口；非演示成员则跳转至其最后一次已知指针位置。

**尚未实现的内容**：

- **非演示场景的持续跟随**——在非演示状态下跟随其他成员的视口尚未实现；目前唯一的到达其他成员画布的方式是上述一次性光标跳转。

- **激光笔同步**（见[激光笔同步不在 v1](#激光笔同步不在-v1)）——线路协议已携带 tool 字段，但激光笔不会广播给协作者。

- **观众可见性**——演示者无法看到谁在跟随自己，也无法看到人数。

**代码做了什么**：`Member.presenting`（中继端临时标志，不持久化）在 `present {active:true}` 时设置，在 `present {active:false}` 时删除；`welcome.peers` 将其传播给后加入者，使其立即看到演示图标。`PresentPayload` = `{active:true}` | `{x,y,z}` | `{active:false}`。`ContentType` 新增 `"present"`——与 `pointer` 同属隐私层级（可见某人正在看向哪里）。视口帧使用 `sendScene` 约 100ms 后缘节流惯例。旧中继静默丢弃未知消息类型；旧客户端忽略它——无需提升协议版本。

### 激光笔同步不在 v1

**现象**：`tool: "laser"` 指针模式不会同步给协作者。

**原因**：ADR 0003 后果清单——激光同步是 1.9 候选。

**代码做了什么**：激光笔迹仅限本地；指针消息类型已携带 tool 字段，线路协议本身
已支持它。

### 房间名对中继为明文（尚未端到端加密）

**现象**：房间共享名（ADR 0004）走**未加密**的 `room-name` 与 `room-probe` 消息，因此中继可以看到它——与今天已提交的明文线路下中继可读场景载荷完全一致。

**原因**：058 的签名加密信封（届时 `room-name` 与探测的 `roomName` 必须装入其中）是将来的工作。在那之前，房间名与场景一样对中继可见；并**没有引入新的泄露类别**。此外，探测会向任何持邀请者返回 `{roomName, snapshotAvailable, peerCount}`——但这也正是他们加入后就会了解到的信息，因此并未增加泄露面。

**代码做了什么**：房间探测门控（ADR 0005）保证了"此房间是空的"提示始终真实；房间名是随房间一起消亡的短生命周期房间内容。

## Peering（跨机画布传输）

设计文档：[ADR 0013](adr/0013-cross-machine-canvas-transfer.md)、
[PEERING.md](PEERING.md)。每条都说明限制是什么、为什么存在、代码对此做了什么。

### 传输线路是明文且可伪造的

**现象**：画布传输（Canvas transfer）在局域网上不加密地传输。同网段的任何人都能观察它，也能伪造一次传输——发送方**完全没有**认证，唯一的门是接收方的人工确认。

**原因**：加密要么需要一套 PKI（ADR 0003 已拒绝——自称身份、不做 mini-CA、不做逐成员吊销），要么需要一套对端 daemon 无法自行引导的 TLS（用户得自己管证书）。v1 选择"接收方确认"而非伪造一个加密身份，把机密性显式延后而不是假装拥有。

**代码做了什么**：要约（Transfer offer）只携带描述性信息（别名、指纹、元素数、字节数、画布名）——不含内容、不含缩略图——画布字节在接收方接受之前不离开发送方。设备指纹**只标识、不认证**；它的存在只是为了让一台机器忽略自己的通告。这正是对 LocalSend 失败模式的正面处理：该项目的发现层 MitM（GHSA-424h-5f6m-x63f，CVSS 9.3）恰恰是"伪造通告冒充已知设备"，因此任何通告都不被当作可信。

**何时重新评估**：当加入匿名的、按要约作用域的加密手段时——它只解除机密性这一半，不解除冒充那一半；后者需要真正的身份体系，不在范围内。

### LAN listener 是第二个表面，默认关闭

**现象**：daemon 会开启第二个监听面（`0.0.0.0`、系统随机端口、由 mDNS 通告），其他机器可达。默认不开，用户显式开启；重启后恢复关闭，除非用户持久化了该设置。

**原因**：loopback 表面承载的是受两道用户同意门控的 agent 控制能力；放宽它等于把 agent 控制悄悄扩到网络上。两个表面不能共用能力集。

**代码做了什么**：LAN listener **只承载画布传输**。它不使用 `originAllowed()`（该函数接受空 `Origin`——而 Go 对端发送的正是空 Origin），也不暴露场景读写、画廊、字体或任何 agent 方法。`excali-bridge lan on|off|status` 是唯一真相源，CLI、托盘与 Options 页都通过它读写。

### 任何平台上都没有自动发现

**现象**：Peering 完全没有零配置发现能力——macOS 没有，Linux 没有，Windows 也没有。对端只能通过**手工交换地址**到达，这是唯一途径。

**原因**：这是对 mDNS/DNS-SD 的**全平台**拒绝，不是某个平台的缺陷。用户态 mDNS 这条路本身不成立：macOS 上 `mDNSResponder` 独占 5353 端口，且系统只把一个组播包投递给单个套接字，自己开端口的库收不到任何东西；而通行绕法（从随机端口回应）违反 RFC 6762 §11，合规对端会直接丢弃。要做对，就得为 macOS 写 cgo 绑定系统 Bonjour API、为 Linux 绑 Avahi——换来一个"一半真实网络都直接拦死"的发现能力（访客 Wi-Fi 开了客户端隔离、企业网做了 VLAN 切分）。

**代码做了什么**：手输地址不是兜底，**它就是功能本身**。`excali-bridge peers` 列出用户手动添加的对端，地址交换就是一次复制粘贴。它在 mDNS 会失效的那些网络里照样能用，所以实践中它是更可靠的那一半，而不是降级的那一半。托盘从不是查看或操作对端的唯一途径。

**何时重新评估**：当出现跨平台、不需要 cgo 或各平台系统 API 的发现方案时（例如受本地网络权限门控的浏览器 API）。在此之前，加 mDNS 等于拿一个能用的复制粘贴，去换一个依赖平台的也许。

### 无人应答的要约会过期，不会排队

**现象**：如果接收方机器上没有连接着扩展页面，要约等待 60 秒超时后失败。没有存储转发。

**原因**：一个对局域网开放的端口同时还会累积无主的画布内容，这比一次失败的传输更糟。

**代码做了什么**：daemon 只在内存中保留要约元数据并带超时，在接受之前不存储任何画布内容。发送方看到的是超时——永远不会静默成功，也不会被错误地报告为"被拒绝"。

### Peering 没有发送端界面

**现象**：画布传输只能从命令行发起
（`excali-bridge peers.transferOffer '{"address":"<ip>:<port>"}'`）。编辑器里有接收侧
（右上角要约浮层），但没有任何「发送」的入口。托盘的 LAN 行也因此隐藏——暴露这个开关
等于宣传一个用户够不着的功能。

**原因**：没有自动发现的前提下，发送端界面也只是一个填地址的表单。手工交换地址是刻意
决策（见上文），所以对话框要用户填的 `ip:port` 和命令行要的一样——UI 只是给这个交互
加了层皮，没有消掉它唯一的难点。真正好用的发送端需要记住的对端设备，或者二维码/链接
式的交接，那是设计工作，不是一个缺按钮。

**代码做了什么**：完整传输链路端到端可用——接收方浮层、确认、200KB 分片、sha256、
画布落地——双机手册（[PEERING-TESTING.md](PEERING-TESTING.md)）有验证步骤。发送端
落地后 LAN 行会回到托盘。

### 托盘的 `Canvas` 行在取消激活后会滞后

**现象**：在编辑器里关掉画布后，Presence 托盘的 `Canvas` 行可能还要几秒才更新，
期间仍显示 `active`，而编辑器按钮已经是 `Activate` 了。

**原因**：托盘按 2 秒周期刷新，而 daemon 的"当前激活画布"是在页面数据连接关闭时
清空的。取消激活现在会立刻关闭那条连接，但两端的轮询周期之间仍留有一个窗口。彻底
消掉它需要推送通道（daemon 主动广播状态变化），而不是把轮询调得更快——那只是多花
CPU 去掩盖同一个竞态。

**代码做了什么**：`toggleActivation` 同步地停掉会话，所以 daemon 在同一轮就看到连接
关闭。托盘仍要等它自己的 2 秒 tick。1.9.0 先保持现状；推送通道是后续工作。


**现象**：CLI 不再随源码树分发。全新 clone 不下载就无法 `ping`，而 `~/.local/bin` 并不在所有人的 `PATH` 里。

**原因**：[ADR 0012](adr/0012-bridge-daemon-is-the-product-presence-is-its-face.md)——在 git 里维护 28MB 交叉编译产物，比加一个下载步骤更糟。

**代码做了什么**：`excali-bridge` 只解析唯一规范路径，版本比较靠询问二进制自身（`excali-bridge version`）而不是看文件名，绝不静默回退到第二份；skill 的 preflight **打印**那一行 `PATH` 导出，而不是去改用户的 shell rc 文件。
